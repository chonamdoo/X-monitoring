https://t.co/PEXIjWYM8B

Build an open-source, production-quality trading charting platform using open-source libraries. Do NOT use TradingView Advanced Charts, proprietary chart SDKs, embedded TradingView widgets, or paid charting components.

Use these as building blocks/reference implementations where useful:
- TradingView Lightweight Charts:
https://t.co/PEXIjWYM8B
- PixiJS:

- uPlot:

- Apache ECharts:
https://t.co/mJuK9ZP6Le

PRIMARY GOAL

Create a modular trading-chart engine that can eventually support a TradingView-style charting experience while allowing any market-data provider to be plugged in.

Do not make a demo. Build the foundation of a real charting product.

CORE CHART

Implement:

- Candlestick, bar, line, area, and Heikin-Ashi charts
- Volume
- Multiple synchronized panes
- Multiple price scales
- Timeframe switching
- Symbol switching
- Smooth mouse/touch pan and zoom
- Crosshair synchronized across panes
- Price/time tooltips
- Autoscaling
- Logarithmic and percentage scales
- Extended-hours sessions
- Session breaks
- Real-time candle updates
- Historical pagination when scrolling backward
- Efficient handling of hundreds of thousands of bars

INDICATOR ENGINE

Create an indicator architecture separate from the renderer.

Include initially:

- SMA
- EMA
- VWAP
- RSI
- MACD
- Bollinger Bands
- ATR
- Volume Profile

Indicators must be dynamically added/removed and able to render either over the price chart or in independent panes.

Design the API so community-created indicators can eventually be loaded as plugins.

DRAWING ENGINE

Implement an independent drawing-object system supporting:

- Trend line
- Horizontal line
- Vertical line
- Ray
- Rectangle
- Price range
- Date range
- Fibonacci retracement
- Parallel channel

Every drawing must support:

- Selection
- Dragging
- Resizing
- Deleting
- Style properties
- Serialization
- Restoration
- Undo/redo

Do not tightly couple drawings to Lightweight Charts internals.

DATA ARCHITECTURE

Do NOT hard-code a market-data provider.

Create interfaces such as:

- MarketDataProvider
- HistoricalBarsProvider
- RealtimeTradesProvider
- RealtimeQuotesProvider

Support normalized events such as:

- Trade
- Quote
- Bar

A market-data provider should be replaceable without changing the charting system.

Build a WebSocket ingestion layer capable of batching high-frequency updates before sending them to the renderer.

PERFORMANCE

Treat performance as a first-class requirement.

Use where appropriate:

- Canvas/WebGL/WebGPU
- Typed arrays
- Object pooling
- requestAnimationFrame batching
- Incremental calculations
- Web Workers for expensive indicators
- Viewport-based rendering
- Intelligent downsampling

Avoid rerendering React/Angular components on every market tick.

The architecture should remain responsive with large historical datasets and high-frequency real-time updates.

UI

Keep the interface minimal and professional.

Desktop-first layout:

Top:
- Symbol search
- Timeframe controls
- Chart type
- Indicators

Left:
- Drawing toolbar

Center:
- Main chart

Right:
- Optional watchlist/details panel

Bottom:
- Optional indicator panes

Use a dark neutral appearance.

Do not waste time building a marketing interface.

Focus on the charting engine.

ARCHITECTURE

Split the project into clear packages/modules such as:

- chart-core
- chart-renderer
- data-engine
- indicator-engine
- drawing-engine
- provider-sdk
- ui

Keep the core engine framework-agnostic wherever practical.

DELIVERABLES

Produce:

1. A working application.
2. Complete source code.
3. README explaining the architecture.
4. Data-provider interface documentation.
5. Indicator plugin documentation.

Four components:

How a trade actually fires:

You design a strategy with Claude → it turns it into questions to ask Jev → Jev reads live data and answers with probabilities → the trade fires against your rules.

Why I've split things this way:

Opus 5.5 handles the thinking that happens once (high-level strategy), and Jev handles the decisions that happen constantly.

The Three Layers of a Reliable AI System
Builders often treat prompt chains, agent loops, and multi-agent graphs as competing ideas
They represent three distinct layers of one system
1. The Harness Layer (Environment and Memory)
The harness consists of everything existing outside model weights
It manages filesystem access, environment variables, authentication tokens, and durable files
Andrej Karpathy established the defining mental model:
The model is the CPU
The context window is the RAM
A raw CPU without storage or an operating system crashes instantly
When users dump twenty pages of background text into a single prompt, they flood the RAM
The model loses attention on critical rules
A clean harness stores project knowledge in external markdown files
It loads only the exact snippet needed for the immediate step
2. The Loop Layer (Evidence and Convergence)
A model outputting code or text needs automated validation
Asking the model "Are you sure this is right?" creates a circular hallucination loop
The model evaluates its own probabilistic prediction and confirms its initial bias
The loop layer introduces objective sensors:
Test runners (pytest, vitest, cargo test)
Format validators (JSON schema checkers, linters)
Execution budgets (maximum four attempts before human review)
The model suggests the correction
The harness runs the test and supplies the raw terminal output
Execution continues only when mechanical evidence confirms the fix
3. The Graph Layer (Work Allocation)
Long tasks crumble when forced into a single endless conversation thread
The graph layer distributes work across isolated execution contexts
One worker analyzes the task and writes an implementation blueprint
A second worker writes the code in an isolated directory branch
A third adversarial worker reviews the diff against project requirements
Context stays clean
No single prompt carries the burden of the entire project lifecycle

You do not need a massive enterprise platform to apply harness engineering
A personal harness requires five mechanical rules in your everyday workflows
1. Turn Every Request into a Bounded Contract
Conversational prompts allow models to silently redefine success
When an ambiguous prompt encounters friction, the model solves an easier adjacent task and reports victory
A production contract sets hard boundaries before generation starts:
Deliverable: Exact file name and format
Constraints: Dependencies allowed, style requirements, token budget
Non-Goals: Explicit list of items the model must avoid touching
Acceptance Criteria: The exact condition required to close the task
Without an explicit contract, the model decides when it finishes
With a contract, the criteria decides when the model finishes

Context degradation strikes every frontier model over long horizons
Dumping an entire project documentation file into chat burns tokens and dilutes focus

The model scans the map, selects the single relevant file, and reads that file alone
A compact map preserves working memory
A giant prompt dump exhausts it
3. Externalize Memory into Durable Files
Chat history serves as temporary scratch space
The conversation thread is not a database

Jev for RAG, clearly explained!

Hybrid search gives you a shortlist. It does not decide which passages contain evidence, which are merely adjacent, or whether the evidence is strong enough to answer.

That missing judgment is where Jev fits.

Jev sits between retrieval and generation. It does not replace BM25, embeddings, or the LLM. It evaluates the candidates they produce before those candidates enter the context window.

→ Retrieve wide

Combine dense and keyword search, then merge the results with reciprocal rank fusion. This gives Jev a broad candidate pool, such as the top 20 passages shown in the visual.

Retrieval still sets the ceiling. If the right passage is missing from this shortlist, Jev cannot recover it.

→ Judge every candidate together

Send the query as Jev’s state. For each candidate, ask a typed yes-or-no question such as “Does C7 help answer this query?”

Jev evaluates every question in one packed request and returns a calibrated probability for each passage. This avoids making a separate model call for every query-passage pair.

→ Let code apply the threshold

Your application compares each probability with a threshold. Candidates above it continue to the LLM. Everything below it is removed before generation.

Jev makes the fuzzy judgment. Code remains responsible for the actual decision.

→ Gate the entire answer

The same request can check whether the retained passages make the query answerable. It can also flag signs of prompt injection inside a candidate.

If answerability falls below the threshold, the application can skip the LLM and return “not in the documents.” The injection score should remain a filtering signal, not a security boundary.

The result is a cleaner division of work.

Hybrid search retrieves broadly. Jev reranks, filters, and decides whether sufficient evidence exists. The LLM writes only from the passages that survive.

Jev’s value here is not simply moving passages up or down a list. It turns relevance into an explicit probability that your application can inspect, threshold, and act on.

To summarise:

- Retrieval finds the candidates.
- Jev decides what deserves context.
- The LLM writes the grounded answer.
